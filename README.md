# Gates

Common security and privacy checks, signed local evidence, and bot delivery for Beyond10x repositories. The Rust CLI and reusable GitHub workflow operate without Atlas. Repositories retain their correctness tests, release requirements and artifacts; Atlas coordinates documentation publication independently.

Install the published Linux x86-64 static binary from the [release](https://github.com/beyond10x/gates/releases), verify it against the release checksums, and put it on `PATH` as `b10x-gates`. Other Unix platforms can build with `cargo install --locked --path .`. Run `b10x-gates bootstrap --directory "$HOME/.config/b10x/gates/bin"` to download the pinned Gitleaks 8.30.1 published binary with its fixed SHA-256 checksum.

## Local use

The policy lives in its own private repository, cloned beside the repositories it guards, and is never copied into candidate source. `install` canonicalises `--policy` to an absolute path and narrows the file to owner-only, so a fresh clone made with the usual umask is accepted and every linked worktree resolves the same file. An administrator enrolls the public key printed by `b10x-gates keygen --output <protected-key-file>`. The policy and signing key stay owned by the current user and unreadable by other users. `B10X_GATES_POLICY`, `B10X_GATES_KEY` and `B10X_GATES_GITLEAKS` select nondefault paths. Never send a private key to CI.

```bash
b10x-gates --repository beyond10x/eventlog --policy ../gates-policy/policy.json install
b10x-gates bot -- commit -m "fix: describe the change"
b10x-gates --repository beyond10x/eventlog check --receipt "$HOME/.local/state/b10x/gates/candidate.json"
b10x-gates --repository beyond10x/eventlog verify --receipt "$HOME/.local/state/b10x/gates/candidate.json"
b10x-gates --repository beyond10x/eventlog publish --receipt "$HOME/.local/state/b10x/gates/candidate.json" --remote-ref refs/heads/fix-example
```

`check` retains a signed receipt and reuses it on retry when it still matches. When a retained receipt for an ancestor of the head, from `--receipt` or the pre-push hook, verifies in full, only the commits it does not cover are scanned; the new receipt still states that every commit since the baseline passed. `verify` invokes no scanners. `publish` verifies the retained receipt, optionally pushes its exact commit, then creates a bot-owned check containing only signed successful evidence. A failed network publication retains the receipt. An enrolled signer is a trusted local runner: its signature establishes origin and integrity, not hardware attestation. Revoking a signer or changing its repository grants invalidates existing evidence.

`install` coordinates `pre-commit`, `commit-msg` and `pre-push` with existing hooks, including worktree hooks. Existing hooks run first, then the gates inspect their final index/message. Reinstallation preserves the chain. A reinstall without `--repository` or `--policy` takes the repository, policy, key and scanner from the installed `config.json`, read through the same owner-only checks, and only for the repository it names; a flag or `B10X_GATES_*` still wins, and with both `--repository` and `--policy` named the file is not read. One copy of the binary is written per repository and the thirteen hook names are hardlinks to it, so an installation costs one binary rather than thirteen. The link holds that exact inode, which is what pins a hook against a binary changing under a commit in flight; the cost is that `cargo install --force` does not upgrade installed hooks, and `install` must be re-run in every repository. `config.json` records the version that installed them. During an authorized migration, `--retire-pre-push-sha256 <exact-old-binary-digest>` retires only that identified pre-push guard; unrelated hooks remain active. No candidate file controls this selection. Local commits require the exact bot author and committer. Hooks are local prevention, not remote authority: GitHub enforcement remains required.

Before committing, the index is scanned independently of unstaged files. Before pushing, every commit since the trusted adoption baseline is inspected, including intermediate commits later deleted from the tip. Push destinations must match the enrolled repository, and directly introduced commits retain the exact organization bot author and committer. Use `--tag <ref>` with `check`, `verify` and `publish` when an annotated tag is part of the evidence; pre-push also inspects tags automatically. A pull request the bot merged through the API is a GitHub-committed merge after the baseline; pre-push and `check` admit a branch or tag cut from it without moving the baseline, through the merge proof below.

`bot` runs `commit`, `tag`, `push`, `fetch`, `merge`, `revert` and `delete-branch`, and checks its arguments before it mints a token. `merge <revision>` and `revert <revision>` take one revision, run Git's `--no-commit` form and commit the result as the bot; they admit long options by exact name only, refuse a merge driver or include in the repository's configuration, an operation in progress and (for `revert`) staged changes, and mint no token. `-- delete-branch <branch>` deletes a remote branch of the repository named by `--repository <owner>/<repo>` or, without it, by the installed hooks' configuration, only when the API shows that it is not the default branch, its classic branch protection is disabled (`protection.enabled`; GitHub's `protected` is true under any ruleset), every rule on it names its ruleset, the restricting rules (`creation`, `update`, `deletion`, `non_fast_forward`) all come from one ruleset and each at most once, no other rule type applies beyond the commit and branch name patterns, and its tip is an ancestor of the default branch. GitHub's REST ref deletion takes no expected tip, so the deletion is a Git push carrying the checked tip (`--force-with-lease=refs/heads/<branch>:<tip>`, run by the verb itself in an empty scratch repository; `push` still refuses every deleting form): a branch that a push moved after the last read is kept, and the refusal names the tip it moved to. `pull`, `rebase`, `cherry-pick` and `am` are refused with the merge route. `push` arguments that delete a remote ref (`--delete`, `-d`, `--prune`, `--mirror`, any prefix Git accepts for them, and `:<branch>` refspecs) are refused with the `delete-branch` route, and the unguarded API route, `b10x-gates api --method DELETE --path /repos/<owner>/<repo>/git/refs/heads/<branch> --output <file>`, for an unmerged branch. The check reads arguments only: a repository's own `remote.<name>.mirror` or deleting push refspec is configuration it cannot see, and the remote ruleset remains the limit. Hook bypass (`--no-verify` and its abbreviations, `-n` in a short cluster), `-c`, `--config-env`, `--exec`, `--receive-pack` and `--upload-pack` are refused. Refusals name their cause: a protected file's path, mode and the mode it needs; a Git verb's exit status, and "nothing staged" when the index holds nothing to commit; for a 4xx API answer the status and GitHub's message, unless the message matches a private rule or a personal path, in which case it is withheld and the status still printed. `api` checks its output directory before the request, and reports a remote write that succeeded as success, with its status, number and URL, even when the response file cannot be written. The API client sends a write (any method but GET and HEAD) once and never along a redirect: a 3xx answer to it is refused, naming the status and saying the write was not repeated. A GET or HEAD follows at most 10 redirects (301, 302, 303, 307, 308), which keeps the redirect GitHub answers for a renamed or transferred repository, and each only when its `Location` is a path on the API host that the client admits for any request (absolute, no `..`, no `#`), written exactly as it is requested; any other redirect is refused unfollowed. A refusal never shows the `Location`, and the credential is never sent to another host.

The bot's Git runs with no global or system configuration and does not take the caller's `GIT_SSL_*` variables or `SSLKEYLOGFILE`. This covers the push, the fetch, the `delete-branch` push and the `ci` fetch. The repository's own configuration is still read, but it cannot change how the bot reaches GitHub:
- Every TLS key it sets for any URL, directly or through an include, is set again to the bot's value, and the bot names each key it overrides. `http.sslVerify` is true, and the CA, client certificate and TLS backend keys are empty.
- A `url.<base>.insteadOf` or `pushInsteadOf` that would move a GitHub URL is neutralised. One that no configuration key can name is refused before Git runs.

A push from `git@github.com:<owner>/<repo>.git` or `ssh://git@github.com/<owner>/<repo>.git` goes over HTTPS as the bot. The credential helper answers only an HTTPS request for a repository on github.com that names no user. A proxy URL with a user, or an `https://<user>@github.com/...` remote, therefore gets no token.

An error about `B10X_BOT_TOKEN`, `GITHUB_TOKEN`, `B10X_GATES_POLICY_GZ` or `B10X_GATES_POLICY_JSON` names the variable and says whether it is missing, empty or not Unicode. It never shows a byte of the value.

`api` and `gh -- api` refuse a write to a ruleset or to branch protection before the policy is read and before a token is minted, naming the path or mutation and saying "ruleset and branch protection changes are the owner's". `api` refuses any method but GET and HEAD on `/repos/<owner>/<repo>/rulesets`, `/repos/<owner>/<repo>/branches/<branch>/protection` and `/orgs/<org>/rulesets` (each with what is below it, and under the `/repositories/<id>/` and `/organizations/<id>/` aliases), judged after percent-decoding (the first decoding strict, at most 8), lowercasing, `.`/`..` segments, repeated or trailing `/` and a query string; it refuses a write whose path cannot be decoded, and a `/graphql` request whose body or query string names `createRepositoryRuleset`, `updateRepositoryRuleset`, `deleteRepositoryRuleset`, `createBranchProtectionRule`, `updateBranchProtectionRule` or `deleteBranchProtectionRule` as a whole GraphQL name (a type such as `UpdateBranchProtectionRuleInput` names none). `gh -- api` refuses, whatever the method, any argument or file an argument names (`--input`, `-F`/`--field <key>=@<file>`, read as UTF-8, UTF-16 or UTF-32) that carries such a path or name, or that is still changing after 8 percent-decodings; standard input (`--input -`, `@-`) and a named file it cannot read; an argument holding `{owner}` or `{repo}` when some owner or name would make it such a path, `{branch}` (which may hold `/`) outside a whole field value such as `head={branch}`, and any placeholder in the GraphQL `query` field (an argument whose placeholders would take more than 4 MiB of fillings to judge is refused as not judged); and an argument holding the header text `Content-Encoding:` or `Transfer-Encoding:`, a comment body that mentions one included. A refusal shows a path found in a file only up to its `rulesets` segment and ruleset id, or its `protection` segment. Reads go through `b10x-gates api --method GET`. A named file is judged on one read, and `gh` reads it again after the token is minted. The App's `administration` permission remains: holding the App key is enough to call the API without `b10x-gates`.

## What is checked

- Gitleaks 8.30.1 scans file bytes, filenames, commit messages and metadata, and annotated tags. The scanner uses its pinned default rules, a trusted explicit configuration, an empty ignore file, and `--ignore-gitleaks-allow --redact=100`. Candidate ignore files and inline comments cannot disable it.
- A private policy checks forbidden associations and identifiers without printing those terms. `forbidden_literals` are matched as escaped case-insensitive substrings; `forbidden_patterns` are case-insensitive regular expressions, for rules a literal cannot express such as a separator or case variant, a bare surname or an adopter's name. `allow_patterns` admit an occurrence only when the pattern's `(?P<admit>...)` group **contains** it, so a real upstream citation — a dependency URL, a cargo `git` source, an ssh remote — need not be falsified, while a markdown link's label, a query string or prose on the same line is still refused. An allowance without that group is refused, as is any rule that matches an ordinary line or the empty one. Allowances never reach `personal-paths`; a policy exception does, as it reaches every rule: it names the exact repository, rule, location, line and line-content digest, so it admits one historical line and nothing beside it (`tests/exception_personal_paths.rs`).
- Linux and macOS home paths and Windows profile paths are rejected, including bare home directories, and in every delimiter this organization writes: backticks, markdown table cells, emphasis markers, quotes, link targets and `file://`. Portable `$HOME`, `${HOME}` and XDG placeholders are accepted. A path that merely contains the word `home`, and a REST route such as `/users/{id}`, are not personal paths: the first segment must end the reference or be followed by `/`, and `/Users/` is matched case-sensitively. Unicode format characters are removed before matching, and a literal a soft wrap split over two lines is still caught. A JSON `"components"` array of hex strings, the form ESS writes for an output directory (`"encoding": "UnixBytes1"`), is decoded into an absolute path and held to the same rule, compact or pretty-printed, so an encoded home directory is refused like its text.
- Workflow action revisions must be exact commits or Docker digests. Workflow permissions must be explicitly declared.
- Planning files, generated files, journals, symlink target bytes and all other tracked blobs are included. Git attributes, hooks, filters, build configuration and candidate tools are never executed by the scanner. Submodules, incomplete history, non-UTF-8 filenames and inputs beyond the documented limits fail closed.

A change is answerable for the lines it introduces, not for the file it lands in. Every changed blob is scanned whole, and a finding whose exact line is already present in that path's previous version is inherited rather than new — so editing one line of a document that already carries a hundred findings is admitted, while adding the hundred-and-first is refused. This applies to the privacy rules and to secrets. A unit with a NUL byte in its first 8 KiB is left to the secret scanner; an archive or an image carries no prose.

An adoption baseline is an exact trusted commit, not a candidate-controlled file. `audit --output <protected-report>` reports findings in that baseline tree separately. Historical exceptions require the exact repository, rule, location, line and content SHA-256 in the protected policy. Single-line privacy rules bind that line's bytes; secret and workflow exceptions bind the entire unit because they can span lines. Changed lines, moved locations and new occurrences require new review. Unchanged files inherited from the baseline are not new violations. No history is rewritten.

It reads full changed blobs per new commit, refuses a blob over 128 MiB, and scans a candidate in batches of at most 256 MiB, each changed file counted with its predecessor, so a candidate's total size is no limit. It deliberately fails instead of silently skipping unsupported content. It does not reuse repository-specific tests or declare a deployment or release complete.

## GitHub enforcement

Adopters call `.github/workflows/common.yml` at an immutable Gates commit from a base-branch `pull_request_target` workflow, and pass only the selected-repository organization secret `B10X_GATES_POLICY_GZ` (or, on a pin before 0.1.21, `B10X_GATES_POLICY`). The same check runs on integrated branch/tag pushes. The job downloads a fixed-checksum Gates binary and pinned Gitleaks binary, then fetches candidate objects into a fresh bare repository using the workflow token, supplied through the environment so it never appears in argv. A pull request's head commit is fetched by its id, because GitHub has served that id while not advertising `refs/pull/<n>/head`; only when the id is refused does `ci` fetch `refs/pull/<n>/head` instead, and the candidate is the id either way. That fallback stays for cross-repository (fork) pull requests, since whether GitHub serves a fork's head commit by id from the base repository has not been verified. A refused fetch names each refspec git refused and git's last message line; the line is withheld when it or any of git's output matches a private rule, a personal path or the workflow credential, and the refspec is still named. On a plan where organization secrets reach public repositories only, a private adopter needs the policy as a repository secret of the same name. `ci` reads `B10X_GATES_POLICY_GZ` when it is set and non-empty, else `B10X_GATES_POLICY_JSON` (which the workflow fills from `B10X_GATES_POLICY`), else the protected policy file; a compressed value that does not decode, decompress within 4 MiB or parse is refused naming the variable, never a fallback. It never checks out the candidate. Private policy is available only to this trusted step, whose children cannot execute candidate code.

The workflow first retrieves bot-published evidence. It verifies Ed25519 signatures, authorized public keys, repository name and immutable numeric id, adoption baseline, exact head, complete commit/tag and object manifest, scanner/tool versions, public/private policy digests and the complete result roster. A valid receipt causes **zero scanner invocations**. Missing, malformed, tampered, incomplete or stale evidence runs the common scanners. Missing policy fails closed.

## Content that never reaches a commit

A pull request body, an issue comment, a release note and a chat message are published without passing through Git, so no hook sees them. The delivery verbs scan before they send: `gh -- <args>` scans its arguments, `api --input <file>` scans the body file, and `scan-text <file>...` refuses any file that breaks a rule, for publishers that are not `gh`. Each refuses with rule coordinates and never echoes the matched text. A missing policy is a refusal, not an unscanned send.

`scan-artifact <file>` validates an executable release artifact without executing it. The supported
format is an ELF64 little-endian `ET_EXEC` or `ET_DYN` file of at most 128 MiB, with no more than
4096 sections and 4096 segments. Its complete section and segment ranges must be in bounds;
file-backed sections may not overlap; compressed sections are refused. The private-identifier and
personal-path policy reads every byte from non-executable sections, preserving its existing UTF-8
and format-character handling. Pinned Gitleaks reads printable runs of any length from those
sections. Both checks additionally read printable runs of at least four bytes from the complete
file. Marking a normal string executable therefore does not hide it, while a three-byte instruction
encoding is not treated as prose. A successful report includes the complete original file's
SHA-256, original, privacy and extracted byte counts, non-null section count, format, and scanner
invocation count. The extraction does not establish that encoded, encrypted, or strings shorter
than four bytes in executable sections contain no private data; unsupported or ambiguous artifacts
refuse rather than receiving an exception.

The boundary: a raw `gh` or `curl` invoked outside `b10x-gates` is unguarded. Route delivery through the verbs.

Require the resulting `Security and privacy` check before integration, retain repository correctness checks separately, and enable GitHub secret scanning and push protection where supported. Initial adoption installs the caller after local verification, observes its first successful main run, then enables the required check. Fork workflows must never receive private policy through a candidate checkout or candidate action.

The policy wire model is strict JSON: `version` (2), random `nonce`, `forbidden_literals`, `forbidden_patterns`, `allow_patterns`, `repositories` (numeric `id` and exact `baseline`), `signers` (Ed25519 `public_key` and explicit `repositories` grants), and bounded `exceptions`. Actual private values have no public example. The nonce prevents the published policy digest from becoming a dictionary oracle. A policy whose pattern does not compile is refused at load, never at first scan. Policy updates arrive as a commit in the private policy repository and reach CI as an organization secret; `policy except --findings <report>` appends reported findings as exceptions so an admitted occurrence is reviewed as a diff rather than hand-edited; `--any-line` binds the content but not the line, and `--any-content` binds a location whose file is regenerated on every build. An exception location ending in `*` covers a tree. A GitHub secret is limited to 48 KB, which the policy outgrew, so the organization secret `B10X_GATES_POLICY_GZ` holds it compressed and encoded, `gzip -9 -c policy.json | base64 -w0`, and that output must stay under 48 KB (line breaks in the value are ignored); `policy publish` is the step that writes it: it fetches the policy repository (`--policy-repository`, default the directory of `--policy`), publishes only `origin/main:policy.json`, never a working-tree file, and is a dry run printing the policy commit, each target and its size unless `--apply` is given, which writes each secret with `gh secret set` (the value on standard input) and reads the names back with `gh secret list`. The targets come from a JSON file (`--targets`, default `<configuration home>/b10x/gates/publish.json`): `organization` (default: the one owner the policy enrols), `plain` to also write the plain `B10X_GATES_POLICY` secrets for callers on older pins, `sliced`, the repositories whose exceptions leave the organization's plain secret for a repository secret of their own, and `compressed`, the repositories (private ones, which the organization secret does not reach) that get the whole compressed policy as a repository secret `B10X_GATES_POLICY_GZ` of their own, written and read back like the others, and whose exceptions also leave the organization's plain secret; a `sliced` or `compressed` repository the policy does not enrol publishes nothing. Any value of 48,000 bytes or more publishes nothing. A marker (`--marker`, default `<state home>/b10x/gates/policy-published`) records the last published policy commit; the same commit again prints `unchanged`, and `--force` publishes anyway; the policy digest is computed from the parsed document and does not change with formatting. Nothing contacts Atlas at runtime.

Every commit after the trusted adoption baseline must have the exact raw Git author `b10x-bot[bot] <316511680+b10x-bot[bot]@users.noreply.github.com>`, `github-actions[bot] <41898282+github-actions[bot]@users.noreply.github.com>` or `dependabot[bot] <49699333+dependabot[bot]@users.noreply.github.com>`. The third is admissible as an author only, so a dependency update can be reviewed and merged; it is scanned like any other change. Candidate construction enforces this before scanning or receipt reuse, including intermediate commits and merged side branches. Mailmaps, display names, duplicate author headers and other bot names cannot authorize a commit. GitHub merge committers remain admissible to the common author check; direct local delivery still requires the exact organization bot as both author and committer. Git metadata establishes this allowlist, while App-only branch authority establishes who can publish it. On a private repository, where the plan offers no rulesets, a GitHub-created merge after the baseline is admitted only as a two-parent merge of a pull request opened and merged by the exact bot account (login, type and numeric id), whose tree is Git's own clean merge of its two parents recomputed locally, and whose every head commit carries the exact bot identity; squash merges are refused there, and the head commits carry the same identity-only proof as direct bot commits to that repository.

Recomputing a merge locally requires Git 2.43.0 or later: `git merge-tree --write-tree` arrived in 2.38.0 and `git --attr-source` in 2.41.0, and 2.43.0 fixed a `merge-tree` crash under `--attr-source`. The local merge reads no attributes from the worktree, and refuses a non-empty `$GIT_DIR/info/attributes`, a configured `merge.default` and any configured `merge.<name>.driver`, so nothing in the checkout running the proof can resolve a conflict.

A version 2 policy is unreadable by an earlier binary: the wire model is `deny_unknown_fields`, so 0.1.2 refuses it with "policy format invalid" and the gate fails closed. Release and roll out 0.1.3 to every caller **before** setting the organization secret to a version 2 policy; local hooks read the policy file directly and can move first.

Version 0.1.3 adds `forbidden_patterns` and `allow_patterns`, widens the personal-path boundary, and scans published content in the delivery verbs; it requires policy version 2 and invalidates earlier receipts through the Gates version and private-policy digest. Version 0.1.1 added the `commit-authorship` result and invalidated earlier receipts through the Gates version and public-policy digest. Version 0.1.2 changes no check, policy field or receipt format, and invalidates receipts retained under 0.1.1 through the Gates version alone. Historical baseline auditing remains separate.

## Development and releases

```bash
cargo build --locked
target/debug/b10x-gates bootstrap --directory "$HOME/.cache/b10x-gates/scanner"
export B10X_GATES_GITLEAKS="$HOME/.cache/b10x-gates/scanner/gitleaks"
cargo test --locked
cargo fmt --all --check
cargo clippy --all-targets --locked -- -D warnings
```

The real-scanner tests fail if Gitleaks is unavailable; they never silently skip. Tests cover index isolation, intermediate commits, metadata/tags, suppression attacks, private-output redaction, hostile candidate files, hook chaining, cryptographic rejection, zero-invocation reuse and ancestor receipt reuse. ESS models the signed receipt and the bot's `merge`, `revert` and `delete-branch` under `ess/`.

`cargo run --locked -- gate` performs the complete repository gate and installs the pinned scanner if missing; CI delegates to this same Rust command.

Release only from gated `main` with a bare annotated version tag. Publish the static Linux binary and `SHA256SUMS`, verify both after downloading them, and verify the GitHub release author is the organization bot before pinning consumers. Build release binaries for `x86_64-unknown-linux-musl` with Rust source-path remapping and validate them with `scan-artifact` before publication. A static glibc build loads the host's `libnss_*` modules to resolve names and crashes on its second GitHub request (0.1.19); `scan-artifact` refuses a static executable that carries glibc's name service switch. Documentation publication and downstream releases are separate operations.
